# 龙头组只剩 1 只（9/15 → 9/16 只显示桂林旅游）· 根因与修复

日期：2026-09-15
范围：`src/logic/auction/dragon-group.js`、`src/logic/auction/dragon-leader-pick.js`、
`src/data/stock-topics.js`、`src/data/dragon-leaders.js`、`db/create_dragon_leaders.sql`

---

## 一、现象

用户 9/15 盘后看 9/16 的看板：**龙头组只有 1 只「桂林旅游」，其它题材的龙头全都不显示**。
且无论刷新多少次都不恢复。

REST 核实（`dragon_leaders`）：

| 评选日 | 行数 | 内容 |
|---|---|---|
| 2026-09-14 | 7 | AI应用/农业/化工/半导体/大消费/液冷算力/电力 |
| 2026-09-15 | **1** | AI应用 → 桂林旅游 `52.18%` `size=3`，写入时间 `2026-09-15T09:17:05Z`（北京 17:17） |

写入时间在收盘权威口径（16:05）之后 —— 说明**不是"算早了"，而是"算的时候输入不全"**。

---

## 二、根因（两条腿都断了，且结果被永久冻结）

### 根因 A：评选时「共享题材库」尚未就绪 → 33/39 只股票全落「其它」

题材归属的常规路径是（`topic-sort.js#getStockTopicArr` /
`topic/rules.js#getTopicGroups`）：

> 当日 `note`/`topics` 为空 → **回退共享题材库** `getStockHistoryTopics()`

而 9/15 的 39 只正式成员里，**有 33 只的 `topics` 字段是空的** —— 也就是说绝大多数股票
**只能靠这份库来分类**。`state._cloudTopicsCache` 由登录后的异步步骤 `loadCloudTopics()` 填充；
若评选抢在它到货之前，这些股票全部落「其它」→ 每个题材都凑不够 3 只 → 只选出 1 只。

**离线复算（同一份 9/15 真实数据，直接调用项目自己的分类函数 `getTopicGroups`）**：

| 状态 | 落「其它」 | 达到评选门槛（成员≥3）的题材 |
|---|---|---|
| 题材库**未**就绪 | 33 / 39 | 1 个（AI应用） |
| 题材库**已**就绪 | 2 / 39 | **4 个**：AI应用(12)、一带一路(8)、农业(8)、CPO(5) |

→ 4 只是「仅用正式名单」的**保守下界**（还没算入观察组继承票），与云端的 1 只差距明显。
对照组 9/14（健康日）：47 只里只有 4 只落「其它」；9/14 名册实际 7 行。**分离度极大，判定可靠。**

### 根因 B：结果被「upsert 只增不删 + 非空即视为已评选」永久冻结

`dragon_leaders` 主键 `(date, topic)`，落库走 `upsert` ⇒ **只增不删**。
补评选的触发条件只判 `rows.length === 0` ⇒ 名册只要非空就再也不补算。
两者叠加：根因 A 产出的那一行残缺**既不会被覆盖、也不会被触发重算**，永久冻结。

### 顺带发现（同类，第三条腿）：`_buildPool` 静默吞掉读取失败

`_buildPool` 读「前一日竞昨高光集」时是 `try { … } catch { 只打一条日志 }` ——
读失败会得到一个**空集**（而不是报错），池子静默少掉「观察组继承票」（往往正是某题材凑够 3 只的关键），
同样会少选/漏选龙头，且结果一样会被落库冻结。违反 §10「读取失败 ≠ 空」。

## 三、修复

### 1. 评选时间口径（明确并写进文件头）

评选**不在**次日 9:25 做，也**不在** 15:00 收盘那一刻做，而是等 `isAuthoritativeCloseReached(T)`
= **北京 16:05**（= worker 收盘重算完成时刻，`dragon-rank.js` 的 `WORKER_CLOSE_HOUR=16` +
`WORKER_CLOSE_BUFFER_MIN=5`）。

为什么不用 16:00 整：15:00~16:05 之间 `market_metrics.change_pct` 很可能仍是 9:25 竞价副本
（worker 16:00 才开始重算），用竞价口径选出的龙一在 16:05 后会被推翻（同一题材先写 A 再写 B）。

执行者仍是**前端**（§6：候选池含「未落库的观察组继承壳行」，worker 只读 DB 无法还原同一份池子）。
触发链：① 打开看板 / 切日期 → `_load` ② 步评选展示日自己的名册；② 每 5 分钟轮询跨过 16:05 后自动补；
③ 盘后无人开着看板 → 名册为空/残缺 → 次日打开看板时 `_load` ①b 步就地补评选（自愈）。

### 2. `§10 题材库就绪闸门`（修根因 A）—— 主修复

`stock-topics.js` 新增 `isTopicLibraryReady()` / `ensureTopicLibraryLoaded()`；
`_computeAndPersist` 在分组之前：

```
未就绪 → ensureTopicLibraryLoaded()（幂等，已就绪则 0 请求）
仍不可用 → 返回空，【不落库、不登记终局】，由轮询/needFill 自动重试
```

### 3. `§10 继承源就绪闸门`（修第三条腿）

评选前 `ensureAuctionDateDataLoaded(prevTradingDay(T))` 并校验
`_isAuctionWatchlistIndexReady(prevT)`；未就绪则不评选、不落库、不登记终局。
同时 `_buildPool` 里「竞昨高光」的读取失败**不再被 catch 吞掉**（抛给调用方）。

### 4. `整表对齐`（修根因 B）—— 主修复

新增 Data 层 `deleteDragonLeadersForDate(date, topics)`（小范围、按题材名精确匹配、带回读校验，§11）
与纯函数 `planRosterReconcile()`（下沉到零依赖叶子 `dragon-leader-pick.js`，可单测）。

权威评选之后：

- `upsert` 本次结果；
- **删掉**「本次分组里成员数 < 3」的题材的旧行 —— 这是让表等于真相的关键；
- 「成员数够、但暂时查不到区间涨幅」的题材 **保留旧行**（那是数据未到、会重试，删了就回不来，§10）；
- 旧名册读不到 → 只写不删（不知道删哪几行，留待下一轮）；
- 与旧名册逐字段一致 → **一个字节都不写**（幂等，几乎零网络往返）。

补评选触发条件从「名册为空」升级为「该评选日收盘口径已权威、且本会话尚未对齐过」
（`needReconcile`）——这样残缺名册会被正确结果覆盖，而不是永久冻结。
对齐后若结论是「该日确实无龙头」，会**重读**一次云端再渲染，避免继续显示已作废的旧行。
